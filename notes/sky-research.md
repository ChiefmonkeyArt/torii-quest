# Sky & Stars Research: Killing the Skydome Wedge Artifact and the "Painted-On" Star Problem

**Context:** Torii Quest currently uses a single `BackSide SphereGeometry` (radius 500) with a GLSL fragment shader painting sky gradient + stars via spherical UV (theta/phi). Two symptoms:
1. A visible triangular wedge/funnel artifact near the zenith — this is a **shading/gradient math issue**, not a UV-seam issue (the classic seam is the 0°/360° "zipper," but a *wedge converging at a point* is almost always the gradient function itself misbehaving as `phi → 0`, or per-vertex color interpolation across a sphere's pole triangles).
2. Stars that look "painted on" rather than floating — this is a **depth-cue / parallax problem**, not strictly a projection problem. A single infinitely-distant dome gives every star identical, static depth relative to every other star, so nothing ever parallaxes, twinkles independently in a spatial sense, or reveals scale. Real skies (and every AAA game below) fake depth with **at least two distance layers**, real point geometry, or per-star size/brightness variance tied to a 3D position.

## 1. Techniques Catalog

### 1.1 Cubemap skyboxes (6-sided)
- **How it works:** Sky is baked/rendered into 6 square faces (or one cross-layout texture) and sampled via direction vector — no spherical UV unwrap, so there is no pole singularity at all, because a cube has no poles.
- **Used by:** Skyrim, Half-Life, GTA (for reflection capture), most Source/idTech-era games.
- **Pros:** Zero pole distortion, zero seam if edges are authored correctly, cheap to sample (`textureCube`/`samplerCube`), trivially supported in Three.js via `CubeTextureLoader` or `scene.background`.
- **Cons:** Static (needs re-bake or a shader-driven cubemap render target for dynamic time-of-day), 6 textures = more VRAM than one equirect image unless compressed, edge seams still possible if the source art doesn't tile across cube faces.
- **Three.js note:** `THREE.CubeTextureLoader` + `scene.background = cubeTexture` bypasses all sphere-UV math entirely — this is often the fastest fix for the wedge artifact because you delete the pole math outright.

### 1.2 Preetham / Hosek-Wilkie / Nishita atmospheric scattering
- **How it works:** Physically-based analytic (Preetham/Hosek-Wilkie) or ray-marched (Nishita) models compute sky color from sun angle, Rayleigh/Mie scattering coefficients, and viewer altitude — evaluated per-pixel as a *function of view direction*, not sampled from a texture, so there's no UV space to have a pole problem in.
- **Three.js has this built in:** [`Sky.js`](https://threejs.org/docs/examples/en/objects/Sky.html) in `three/addons/objects/Sky.js` — a straight port of the Preetham model, drop-in, no textures.
  ```js
  import { Sky } from 'three/addons/objects/Sky.js';
  const sky = new Sky();
  sky.scale.setScalar(450000);
  const phi = THREE.MathUtils.degToRad(90);
  const theta = THREE.MathUtils.degToRad(180);
  sky.material.uniforms.sunPosition.value =
    new THREE.Vector3().setFromSphericalCoords(1, phi, theta);
  scene.add(sky);
  ```
  ([three.js docs](https://threejs.org/docs/pages/Sky.html))
- **Why this fixes your wedge:** Because the shader evaluates scattering directly from the world-space **view ray direction** (dot products with sun direction, altitude terms) rather than interpolating `theta/phi` UVs across triangles, there is no pole to converge weirdly at. The "zenith" is just `viewDir.y ≈ 1`, a smooth continuous scalar, not a coordinate singularity.
- **Cons:** More expensive per-pixel math than a texture lookup (though still trivial for modern GPUs — this is the classic "cheap enough for 2010s mobile" model). Hosek-Wilkie/Nishita give more physically accurate horizon color but are heavier; Preetham is the right performance/quality tradeoff for a 60fps browser game.
- **Deep dive with full derivation and code:** Maxime Heckel, ["On Rendering the Sky, Sunsets, and Planets"](https://blog.maximeheckel.com/posts/on-rendering-the-sky-sunsets-and-planets/) — ray-marched Rayleigh + Mie + ozone absorption, built for React Three Fiber/Three.js, includes a **LUT-based optimization** (transmittance LUT, sky-view LUT, aerial-perspective LUT) based on Sebastian Hillaire's production paper, which moves the expensive raymarch off the per-pixel hot path into a handful of small precomputed textures regenerated only when sun/atmosphere params change — directly relevant to your 60fps constraint.

### 1.3 Instanced point sprites for stars (real 3D positions)
- **How it works:** Each star is a `THREE.Points` vertex (or an instanced billboard) with an actual `(x, y, z)` position on a very large sphere/shell, rendered with `gl_PointSize` attenuated by distance and a custom fragment shader for the "glow dot" shape.
- **Why it solves "painted on":** Because stars are real geometry at a real distance, they respond to camera **rotation with proper perspective** (near stars parallax very slightly against far ones if you use two shells — see 1.6) and can be depth-sorted/culled, given individual per-star brightness/color/twinkle phase as vertex attributes, and rendered with additive blending for genuine bloom, all of which a painted gradient texture cannot do convincingly.
- **Reference code:** [Ben Podgursky, "Procedural star rendering with three.js and WebGL shaders"](https://bpodgursky.com/2017/02/01/procedural-star-rendering-with-three-js-and-webgl-shaders/) — real per-star size falloff by camera distance; [three.js starfield gist](https://gist.github.com/GraemeFulton/22fc3fb72a14ce4711c2) and [Noah Hradek, "Starfield in THREE. Using point clouds and point geometry"](https://medium.com/@noahhradek/starfield-in-three-e850466ebbdf) — both use `THREE.Points`/`BufferGeometry` with real 3D positions rather than a painted dome.
- **Pros:** Solves the "floating" problem directly, near-zero draw calls (one `THREE.Points` mesh for thousands of stars), GPU-cheap.
- **Cons:** Need to manage point size attenuation carefully across DPI/resolution or stars look inconsistent; additive blending can cause banding on low-color-depth displays without dithering.

### 1.4 Particle systems (three-nebula, THREE.Points)
- **How it works:** Full particle engine (emitters, behaviors, lifecycle) instead of a raw buffer geometry. [`three-nebula`](https://github.com/creativelifeform/three-nebula) is the actively maintained WebGL particle engine for Three.js ([three-nebula.org](https://three-nebula.org/)), MIT licensed.
- **Relevance to stars specifically:** Overkill for *static* stars (plain `THREE.Points` is lighter and simpler — see 1.3), but genuinely useful for **shooting stars, nebula dust, aurora particles, or drifting motes** layered on top of a static starfield for extra "living sky" feel.
- **Cons:** Adds a dependency and bundle weight (~30-50KB min+gzip depending on version) — given your ~50KB sky budget, only pull this in if you want dynamic sky *events*, not for baseline stars.

### 1.5 Video/image plate skies
- Rare in games (common in film) because they don't respond to time-of-day/weather logic and are heavy in file size relative to a procedural shader. Not recommended for Torii Quest — mentioned for completeness. Occasionally used for stylized/2D-plane backdrops in mobile or narrative games where the sky never needs to react to gameplay.

### 1.6 Volumetric / ray-marched skies (Red Dead Redemption 2, Horizon)
- **RDR2:** Full volumetric cloud and fog system using camera-frustum-aligned 3D "froxel" textures (a technique DICE detailed in a 2015 presentation, "Physically Based and Unified Volumetric Rendering") — light scatters through cloud density fields in real time, giving genuine 3D cloud shape and light shafts rather than a flat sky texture. ([Digital Foundry tech analysis](https://www.youtube.com/watch?v=Dnzuh6I8gnM))
- **Horizon Zero Dawn/Forbidden West:** Similar volumetric cloud raymarching integrated with time-of-day.
- **Pros:** The gold standard for realism and depth.
- **Cons:** Heavy — froxel volumes and multi-step raymarching are console/high-end-GPU techniques, generally **not appropriate for a 60fps mid-range-hardware browser game**. Worth knowing about, not worth implementing directly; Maxime Heckel's ray-marched atmosphere (1.2) is the browser-appropriate distillation of the same underlying math (Rayleigh/Mie scattering) without full volumetric clouds.

### 1.7 The "star sphere" trick — separate rotating inner sphere, farther out, for parallax
- **Concept:** Two (or more) concentric spheres: an outer "deep stars" shell that rotates very slowly (or not at all, simulating fixed stars) and an inner "near stars/haze" shell that can rotate at a different rate or respond slightly to camera movement, producing a subtle parallax cue between layers even though both are still "infinitely far" in absolute terms.
- **This is exactly the mechanism Skyrim and most open-world games use** (see §2), and it is the single highest-leverage fix for your "painted on" complaint: **even a 2-layer trick reads as "floating in space with depth" versus one flat dome.**
- **Practical Three.js implementation:** two `THREE.Points` clouds at different radii (e.g., r=400 "bright/near" stars, r=480 "dim/far" stars), independent slow rotation speeds, inner layer slightly larger point size + more twinkle amplitude. Costs almost nothing extra — same draw call count, same shader complexity, just two buffers instead of one.

### 1.8 BOTW's "diorama" sky — painted texture + subtle parallax clouds
- Breath of the Wild's sky is fundamentally an authored/painted gradient dome (its watercolor-inspired art direction extends to the sky), but cloud layers are separate rotating/scrolling mesh layers at different apparent distances above the painted backdrop, giving the diorama-like sense of depth despite a flat-shaded look. Confirmed by [Digital Foundry's BOTW technical analysis](https://nintendowire.com/news/2016/07/02/tech-analysis-legend-zelda-breath-wild/) and the [GDC 2017 talk "Breaking Conventions with The Legend of Zelda: Breath of the Wild"](https://www.youtube.com/watch?v=QyMsF31NdNc).
- **Relevance:** Proves that even a deliberately "flat/painted" art style benefits from at least one extra parallax layer — you don't need physical accuracy, you need **one more depth cue than a single dome provides.**

### 1.9 Sky dome UV projection tricks (equirectangular vs. cube unwrap vs. octahedral)
- **Equirectangular (theta/phi UV, what you're using now):** Cheap, single texture, but has a genuine mathematical pole singularity — at `phi = 0` (zenith) *every* `theta` value maps to the same point, so any texture detail or vertex-interpolated color there is being asked to "converge" infinitely many directions into one point. If your gradient function or noise function isn't specifically built to be pole-safe (e.g., using `1 - phi/piMax` style linear falloffs that don't saturate/clamp correctly, or star cell hashing keyed on `theta` that produces degenerate cells as `sin(phi) → 0`), you get exactly the triangular wedge you're describing — it's the geometric consequence of lines-of-longitude bunching up at a pole, visualized.
- **Cube unwrap / cubemap sampling:** No poles, ever — a cube has no polar coordinate at all, direction is sampled directly, sidestepping the entire class of bug.
- **Octahedral mapping:** Packs a full sphere of directions into a single square texture with a fold in the middle (used heavily for normal-map/environment compression in modern engines). Complex to author manually, but eliminates smearing at poles better than equirect while keeping a single 2D texture (unlike 6-image cubemaps). Overkill for Torii Quest's stated budget — mentioned for completeness since it's a known professional answer to "equirect pole problem."
- **Practical recommendation for your bug specifically:** Given the wedge is a *shading issue*, not fundamentally a projection issue (per your own diagnosis), the fix is almost certainly one of:
  1. Never let your gradient/star-density function depend on `theta` in a way that isn't multiplied by `sin(phi)` (this is the standard "solid angle element" compensation — without it, contributions from cells near the pole are over/under-weighted because equal `(theta, phi)` steps cover wildly different actual sky area near vs. away from the zenith).
  2. Compute star cell hashing and gradient blending in **view-direction (Cartesian) space**, not UV space — hash `normalize(worldPosition)` directly instead of `vec2(theta, phi)`. This guarantees continuity at the pole because Cartesian direction has no coordinate singularity.
  3. If keeping UV-based approach, clamp/smoothstep near `phi≈0`/`phi≈π` explicitly rather than letting a `pow()`/division blow up or a cell grid produce degenerate slivers (this mirrors the exact same class of fix the [precomputed atmospheric scattering project](https://github.com/ebruneton/precomputed_atmospheric_scattering/issues/26) needed for a different but structurally similar rendering artifact: "Hack to avoid rendering artifacts... smoothstep near zero").

## 5. Novel Approaches (beyond the standard catalog)

- **Cartesian-space star hashing instead of UV-space:** Rather than hashing `(theta, phi)` cell coordinates for star placement (which is what's almost certainly causing part of your wedge/degenerate-cell problem near the pole), hash directly on `normalize(worldPosition)` — e.g. quantize the unit direction vector into a coarse icosahedral or cube-face grid, then hash that cell ID. This guarantees uniform star density across the entire sphere (no pole clustering/thinning) and has zero coordinate singularity, while still being a single fragment-shader technique with no extra geometry.
- **Screen-space starfield sampled from a small tiling texture, reconstructed from view direction:** Instead of procedurally computing star positions in the fragment shader every frame, precompute a small (e.g. 512×512) tileable "star noise" texture once, and sample it using a triplanar-style projection of the normalized view direction (blend of 3 axis-aligned 2D lookups weighted by direction, similar to triplanar terrain texturing). This avoids *both* the UV pole problem and the per-pixel procedural noise cost, trading it for a single cheap texture fetch — likely to be faster than your current approach while being naturally seamless (no dome UVs at all, since the lookup is direction-driven).
- **Instanced billboard stars with simple LOD by apparent magnitude:** Treat bright stars (say, top 200 by brightness) as individually instanced quads that always face the camera (`billboarding`) and only fade in near dusk, while the remaining thousands stay as cheap `THREE.Points`. This mixed-LOD approach mirrors how Elite Dangerous/Space Engine only "really" render nearby/bright stars in detail while the rest is statistical noise — gives your brightest stars actual sprite-shape twinkle/glow without paying full per-star shader cost for every star in the sky.
- **Dual-shell parallax with independent slow rotation (cheapest "floating" fix):** As described in §1.7 — two `THREE.Points` clouds, different radius, different rotation rate. This is the single cheapest (near-zero additional draw calls, no new dependencies) fix directly targeting your "stars look painted on" complaint, and it's exactly the mechanism Skyrim uses (separate star layer from skybox) generalized to two star layers for parallax depth.
- **Real NASA night-sky HDRI as a *base layer only*, procedural points on top:** Use a small (1-2K) NASA Deep Star Maps or ambientCG night-sky HDRI purely as dim ambient "sky glow"/Milky Way band background (very cheap, static, no shader cost, sampled once via `scene.background`/environment), then layer your existing procedural point-based bright stars on top for the "floating" foreground layer. This gives you the free realism of a real photographed/scientific sky texture for the subtle stuff (haze, Milky Way band, faint field stars) while keeping full programmatic control (twinkle, brightness, color) for the stars that matter visually — and completely sidesteps needing your gradient shader to also solve "stars" since the two problems (sky color gradient vs. star points) are now fully decoupled into two independent, individually simple systems.

## Recommended Next Move

Given the "no paid assets, ~50KB budget, 60fps mid-range" constraints, the highest-value, lowest-risk sequence is:

1. **Fix the wedge first, independent of everything else.** Swap your zenith gradient math from UV-space (`theta`, `phi`) to Cartesian view-direction (`normalize(worldPosition)`), specifically weighting/clamping any pole-adjacent term by `sin(phi)` or, better, just using `viewDir.y` (a smooth scalar from -1 to 1) as your height/gradient parameter instead of `phi` directly. This alone, with zero new dependencies, likely kills the wedge — it's a math bug, not a missing-technique problem, exactly as you suspected.
2. **Decouple stars from the sky gradient shader entirely.** Move stars into their own `THREE.Points` mesh with real 3D positions on a slightly-larger-radius sphere (a "star sphere," §1.7), hashed in Cartesian space, using per-star brightness/size vertex attributes and additive blending. This is a small, self-contained change (well within 50KB) and directly fixes "painted on," because points are now real distant geometry rather than a shaded surface pattern.
3. **Add a second star shell at a different radius/rotation speed** for the parallax depth cue that BOTW and Skyrim both rely on — cheap, no new libraries, biggest perceptual win per line of code.
4. **If you have any headroom left in the 50KB budget, swap the sky-color gradient itself for `three/addons/objects/Sky.js` (Preetham)** rather than hand-rolled gradient math — it's already in three.js, pole-safe by construction (view-direction-driven, not UV-driven), physically plausible for free, and removes an entire class of future gradient bugs.
5. **Treat volumetric clouds, LUT-based Hillaire scattering, and real star-catalog data (Hipparcos) as stretch goals**, not requirements — they're the AAA/space-sim answer to a problem you can already solve with the three steps above at a fraction of the complexity and computational cost, appropriate for your performance target.
